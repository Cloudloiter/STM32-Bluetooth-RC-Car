# 排障日志

记录这个项目里遇到的非显而易见的问题。每个案例都按 **现象 → 排查 → 根因 → 修复 → 教训** 组织。

这些坑大多不是"代码写错了"，而是硬件特性、工具默认配置、以及对自己代码状态的误判。
记下来是因为它们会重复出现。

---

## 案例 1：通电后只有左电机转，右电机完全不动

**时间**：Day1 装车当天
**现象**：电池盒接到 L298N 的 VM 后，左电机（OUT1/OUT2）转，右电机（OUT3/OUT4）毫无反应。ENA/ENB 的跳线帽确认在位。

### 排查过程

1. **怀疑电机坏了** → 把左右电机线对调，结果"不转的仍然是不转的那一路"，说明电机本身没问题
2. **怀疑 L298N 通道坏了** → 交叉互换后仍在同一侧失效，不能排除
3. **单线实验（决定性）**：只拿一根杜邦线，一端接 GND，另一端去碰任意一个 IN 脚
   - 碰到哪个 IN 脚，对应的那对输出就转起来
   - 单根接 5V 则完全不转
   - 手指碰引脚没有任何反应

### 根因

该 L298N 模块的 **IN1~IN4 引脚自带内部上拉电阻**。

- IN 脚悬空 → 被上拉到高电平 → (IN3, IN4) = (1, 1) → **H 桥处于刹车状态**
- 这是模块的**安全默认设计**，不是电平随机或接触不良

装车阶段 IN1/IN2 用桥接线接着（悬空导致实际是高电平），IN3/IN4 完全没接线，
所以右轮被锁死在刹车状态。单线接 GND 等效于给 IN 脚一个确定的低电平，
所以一碰就转。

### 修复

接入单片机的 GPIO 后问题自然消失 —— 因为 PB0/PB1/PB10/PB11 会主动输出确定电平，
不再是悬空状态。

### 教训

- **"引脚悬空"不等于"电平未知"，很多模块会主动上拉成某个确定状态**。
  遇到"一半正常一半不动作"，先怀疑悬空，而不是怀疑器件坏了。
- 手摸引脚没反应，说明不是人体感应/浮空噪声问题，可以直接排除一类猜想。
- 单线接 GND/5V 去碰引脚，是判断数字输入有效电平的**最低成本实验**，
  比拆线、换件、量电压都快。

## 案例 2：手机发指令，单片机一个字节都收不到（耗时最久）

**时间**：Day3 蓝牙联调
**现象**：手机 App（ASCII 模式）发送 `F`，手机端不回显、车轮不动。
手机屏幕上还间歇性刷出乱码。

这是整个项目最耗时的一个问题，前后排查了约四小时。

### 第一阶段：误判方向（走了弯路）

最初的推测链是错的，记录如下以免重复：

1. **怀疑 App 数据格式** → 之前用 HEX 模式发的是 `0x0F`，改成 ASCII 发 `F`，无变化
2. **怀疑波特率不匹配** → 写了一个波特率扫描固件（9600/19200/38400/57600/115200/4800 六档，
   每 5 秒自动切换，用 LED 闪 N 下指示当前档位）→ 六档全部乱码
3. **怀疑单片机自己在乱发** → 写"静默测试"：单片机一个字节都不发，只闪 LED
   → 手机不再刷乱码，**证明乱码确实是单片机发出的，不是线路噪声**
4. **顺这个线索查下去，发现固件还停在自检模式**：
   `UART_SELFTEST_MODE` 宏仍然是 `1`，导致：
   - 每 300ms 往 PA9 发一个 `0x55` —— 手机上的"乱码"就是这些字节
   - `switch(cmd)` 整段被 `#if !UART_SELFTEST_MODE` 排除，**指令解析根本没被编译进固件**
   - `Car_Stop()` 被强制调用
   
   关掉诊断宏、回到正常模式后，乱码消失，但**数据依然收不到**。

> **教训 A**：排查前先确认自己烧进去的到底是哪份代码。
> 诊断用的宏开关如果没有全部归零，后面所有实验的结论都是不可靠的。

### 第二阶段：确认硬件（关键突破）

数据全无，需要判断是"单片机收不到"还是"模块没发出去"。

**步骤 1：单片机侧自检**
把 PA9 和 PA10 用一根杜邦线直接短接，让单片机自己发 `0x55` 自己收，
用 LED 指示结果：每 2 秒快闪 3 下 = 收发正常。
→ **结果：通过。PA9 发送、PA10 接收、串口外设、中断全部正常。**

**步骤 2：万用表误判**
量模块 TXD 引脚空闲电压，读到 **0.98V**（TTL 串口空闲应该是 3.3V）。
一度判断"模块 TXD 输出级损坏"。

**步骤 3：USB-TTL 交叉验证（扭转局面）**
手上有一个 CH340 的 USB-TTL，用它绕开蓝板和蓝牙，直接和模块对话：

- 先做 **环回测试**：CH340 的 TXD 和 RXD 短接，发 `HELLO123` → 原样收回
  → **证明 USB-TTL 工具和驱动完全正常**
- 再把模块的 EN 脚接 3V3 后断电重上电（进入 AT 模式，固定 38400），发 AT 指令：

```
AT            → OK
AT+VERSION?   → +VERSION:2.0-20100601
AT+NAME?      → +NAME:HC-05
AT+ADDR?      → +ADDR:0025:03:D028E1
AT+UART?      → +UART:9600,0,0        ← 波特率正确
AT+ROLE?      → +ROLE:0                ← 从机模式正确
AT+PSWD?      → +PSWD:1234
AT+STATE?     → +STATE:INITIALIZED
```

→ **模块完全正常，8 条指令全部有回应。之前"TXD 只有 0.98V 所以模块坏了"的判断是错的。**

> **教训 B**：怀疑某个器件损坏之前，先用已知良好的工具做交叉验证。
> 万用表测浮空引脚会读到 1V 左右的中间值，这个读数**不能证明信号存在，也不能证明器件损坏**。

### 第三阶段：定位到具体引脚配置（真正的根因）

**步骤 4：给固件装诊断仪表**
在固件里加了两级指示，让"有没有收到数据"变成肉眼可见：

- PC13 每 2 秒亮 150ms = 程序在跑
- **每收到一个串口字节就额外亮 150ms** = 单片机确实从 PA9 收到了东西

**步骤 5：用仪表二选一**
手机发 `F`，PC13 依然保持 2 秒一次的节奏，没有额外闪烁
→ **单片机一个字节都没收到，问题在 PA10 这条输入路径上。**

**步骤 6：量电平，发现异常值**
万用表直流档，黑笔接 GND，红笔量 PA10：**0.99V**。
再量模块 TXD：**0.99V**（两者是同一根线连着，所以读数一致，这个一致不能说明线路通）。

**0.99V 既不是 3.3V（高电平）也不是 0V（低电平）——这是典型的浮空/高阻读数。**

**步骤 7：根因确认（决定性洞察）**

把两个事实放在一起看：

| 场景 | 接收端引脚配置 | 结果 |
|---|---|---|
| 同一根线接 CH340 | CH340 的 RXD **内部自带 10kΩ 上拉** | ✅ AT 指令通信正常 |
| 同一根线接 STM32 PA10 | CubeMX 生成的 **`GPIO_NOPULL`（浮空输入）** | ❌ 一个字节都收不到 |

HC-05 模块的 TXD 输出经过内部限流电阻，驱动能力偏弱。
接在浮空引脚上时，整条线被吊在 1V 左右，**STM32 判定不出高低电平，UART 解析不出任何有效位**。

而 CH340 因为它自己的 RXD 有上拉，把弱驱动信号"拉"到了足够高的电平，所以能正常通信。

### 修复

`stm32f1xx_hal_msp.c` 里 CubeMX 给 PA10 生成的是：

```c
GPIO_InitStruct.Pin  = GPIO_PIN_10;
GPIO_InitStruct.Mode = GPIO_MODE_INPUT;
GPIO_InitStruct.Pull = GPIO_NOPULL;    // ← 问题所在
```

但直接改这个文件，下次 CubeMX 重新生成代码会被冲掉。
所以改在 `main.c` 的 `USER CODE 2` 区，**并且必须放在 `HAL_UART_Init()` 之后**
（因为初始化过程会调用 `MspInit` 再配一遍 GPIO，放前面会被覆盖）：

```c
{
  GPIO_InitTypeDef rx_init = {0};
  rx_init.Pin  = GPIO_PIN_10;          /* USART1_RX */
  rx_init.Mode = GPIO_MODE_INPUT;
  rx_init.Pull = GPIO_PULLUP;          /* 空闲时被拉到 3.3V，才能识别起始位 */
  HAL_GPIO_Init(GPIOA, &rx_init);
}
```

改完后 PA10 电压从 0.99V 变成 **3.27V**，手机发 `F`，PC13 立刻闪了一下，车轮转起来了。

### 教训

- **UART 的 RX 引脚一律配内部上拉，不要用浮空输入。**
  这是行业惯例，不是可选项 —— 浮空输入只有在对方驱动能力很强时才碰巧能用。
- **`GPIO_NOPULL` 是 CubeMX 的默认值，但默认值不等于正确值。**
  外设初始化完成后手动改配置时，一定要注意执行顺序（HAL 库的 `MspInit` 会覆盖）。
- **万用表读数的语义比数值更重要**：0V / 3.3V 是有效电平，1V 左右是浮空，
  卡在中间的值永远先怀疑浮空而不是"电压不够"。
- **"同一条线接 A 能用、接 B 不能用"，问题通常在 B 的输入配置上**，
  而不在这条线本身。

## 案例 3：电机一转，蓝牙立刻断线

**时间**：Day3 功能验证阶段
**现象**：发 `F` 后车轮刚开始转，手机端 HC-05 就断开连接。此时电机甚至是空载（未装车、无轮子）。

### 分析

检查供电链路发现三个 5V 源挤在同一个节点上：

```
4节5号电池 5.72V ──> L298N 的 78M05 稳压 ──> 4.37V ──┐
电脑 USB ──> ST-Link ──> 蓝板 5V ──────────────────────┼──> 蓝板 + HC-05
                                                       ┘
```

**关键计算**：L298N 板载的 **78M05** 三端稳压器要求输入比输出高 **2V 以上**才能稳定输出 5V。
电池 5.72V 的压差只有 0.72V，稳压器已经在失效边缘工作（实测输出只有 4.37V）。

电机启动瞬间的浪涌电流把电池电压进一步拉低，78M05 输出跌到 3V 以下，
HC-05 和 STM32 一起欠压复位 —— 蓝牙连接断开、程序从零重启。

### 修复

**控制电源与动力电源分离，两路只共地不共电**：

- 蓝板 + HC-05 由 **ST-Link（电脑 USB）** 供电 —— 干净、稳定、不受电机影响
- 电池只接 L298N 的 VM+/GND，负责电机驱动
- **L298N 的 GND 必须连到蓝板 GND**（共地）：
  两块板不共地，信号没有共同的参考零点，PA6/PA7 输出的高低电平对 L298N 来说就是乱码

调整后电机全速运转，蓝牙连接保持稳定。

### 长期方案

电池组换成 **6 节 5 号（9V）** 或 **2 节 18650（7.4V）**，
让 78M05 有足够压差正常工作，才能脱离电脑独立运行。

### 教训

- **线性稳压器的压差（dropout）是硬指标，不是"差不多就行"。**
  78M05 需要 2V+，用 6V 电池供 5V 是典型的错误设计。
- **电机负载是电源的最严苛考验。** 空载和堵转的电流能差 5~8 倍，
  电源余量必须按最坏情况留。
- **控制地和动力地要共，电源不要共。** 这是嵌入式项目的基本供电架构。

## 案例 4：串口通了，但每个字节都错 1 个 bit

**时间**：Day3 收尾阶段（案例 2 修复后、电机真正转起来时）
**现象**：指令能收到、电机能转，但手机端的回显开始大面积出错：

```
TX F → RX B      TX L → RX D      TX R → RX V
TX 9 → RX (无回显)    三次发送全部如此，错误率接近 100%
```

### 第一步：先分清"逻辑 bug / 随机噪声 / 信号完整性"

把收发的字节**按二进制位对齐**，逐位比较：

| 发送 | 收到 | 差异 |
|---|---|---|
| `F` = `0100 0110` | `B` = `0100 0010` | 只错 **1 位**，该位被读成了 0 |
| `L` = `0100 1100` | `D` = `0100 0100` | 只错 **1 位** |
| `R` = `0101 0010` | `V` = `0101 0110` | 只错 **1 位**，该位被读成了 1 |

三条判据直接排除了两个方向：

- **只错 1 位** → 不是逻辑 bug（逻辑 bug 会整字节错），也不是随机噪声（噪声通常错多位）
- **错法可重复** → `F` 三次全变 `B`，`L` 三次全变 `D`，这是**固定规律**，说明是电气层面确定性的失真
- **`9` 三次完全没有回显** → `9` 是合法指令，收到就一定会回显；没回显说明它被收成了**非法字符**而被白名单丢弃
  → 由此判定：错误发生在 **模块 TXD → PA10（单片机接收方向）**

### 根因

回到案例 2 里那个被忽略的读数：模块 TXD **空载时只有 0.99V**，加上 STM32 内部上拉后才到 3.27V。

这说明模块的 TXD 是**弱输出**：它拉低是有效的，但**高电平几乎完全靠 STM32 内部的 40k 弱上拉充上去**。

```
上拉电阻 40k × 线缆电容 → 上升沿要几十 µs 才能爬到判决电平
9600 波特率下，一个位只有 104 µs
→ 采样点正好落在"半山腰"，位与位的交界处被读错
```

**旁证**：同一根线接 CH340 时 AT 指令通信完全正常 —— 因为 CH340 的 RXD 内部是 ~10k 强上拉，且按 5V 逻辑判决，余量比 STM32 大得多。这个对比在案例 2 里是解药，在这里是确认。

### 修复（零成本）

**降低波特率，用时间换建立时间**：

- 固件侧：`UART_BAUD_TEST` 9600 → **2400**（每位从 104µs 变成 417µs，余量 ×4）
- 模块侧：`AT+UART=2400,0,0`（AT 模式波特率仍固定 38400，改完用 38400 复查）
- 顺手把 `HAL_UART_Transmit` 的超时从 5ms 放宽到 20ms —— 2400 下 1 字节要 4.2ms，
  原超时太贴边，偶发一次超时就会把 `gState` 卡在 `BUSY_TX`，之后彻底发不出去

**结果**：`S`/`L`/`R`/`9` 各发 3 次，共 12 次回显全部原样返回。

### 治本方案（可选）

在模块 **TXD 与 3V3 之间加一个 4.7k~10k 的上拉电阻**，把 40k 的内部弱上拉换成外部强上拉，
之后就可以回到 9600。遥控指令的带宽需求极低，留在 2400 也完全够用。

### 教训

- **"只错 1 个 bit"是一个强判据** —— 它几乎必然指向信号完整性（电平 / 边沿 / 时序），
  而不是代码逻辑。看到整字节乱、且不可重复，才是噪声。
- **某字符完全没有回显，可以反推错误发生在哪个方向** —— 前提是固件有"白名单 + 只回显合法指令"的设计。
  这个当初为了防噪声写的小设计，最后成了定位方向的关键工具。
- **降低波特率是排查 UART 底层问题的标准手段**，成本为零、破坏性为零，
  而且它同时能排除"波特率不匹配"和"边沿太慢"两类问题。
- **同一个读数在不同阶段含义不同** —— 案例 2 里 0.99V 帮我们定位了浮空输入，
  案例 4 里同一个数字揭示了 TXD 驱动能力不足。数据不会变，解读在变。

## 方法论总结

这几个问题加起来，最有价值的其实是排查方法本身：

1. **先确认自己的代码状态再查硬件** —— 诊断宏没关干净，后面所有实验都是白做
2. **用已知良好的工具做交叉验证** —— CH340 环回测试十分钟就排除了"工具坏了"这个变量
3. **把"看不见的状态"变成"看得见的信号"** —— LED 诊断仪表比反复猜快十倍
4. **给结论设一个可证伪的判据** —— "灯闪成一片 = 收到了"这种二值判据，
   比"感觉好像有反应"可靠得多
5. **读数要解读语义，不只看数值** —— 0.99V 的意义是"浮空"，不是"电压低"
6. **换一个角度重读同一个现象** —— "CH340 能收、STM32 不能收"这个对比，
   才是解开整个问题的钥匙
7. **串口出错先做"按位对齐对比"** —— 这是区分三类故障最快的办法：
   - 只错 1 位且可重复 → 信号完整性（电平 / 边沿 / 时序）
   - 错多位且不可重复 → 随机噪声
   - 整字节全错、完全无响应 → 波特率不匹配或接线方向错
8. **结论要能被数据推翻** —— 这一晚推翻过两次自己的判断
   （"TXD 烧了" → 其实模块完好；"线松了" → 其实边沿太慢），
   每次都靠新的读数而不是靠继续推理。推翻得快，才走得快。
